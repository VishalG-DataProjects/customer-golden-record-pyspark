# customer-golden-record-pyspark
End -to-end PySpark project to create Golden Customer Record by reconciling CRM and Transaction data 
# Golden Customer Record

Builds a single, reconciled "golden" customer dataset from two sources:

- `crm_customers.csv` — CRM registration and profile data
- `transaction_customers.csv` — customer details captured at purchase

The pipeline cleans each source, matches records that describe the same
customer across both systems, and merges each match into one golden record.

## Files

| File | Purpose |
|------|---------|
| `main.py` | The pipeline: load, clean, match, merge, write output |
| `test.py` | Unit tests for the cleaning, matching, and merging logic |
| `golden_customers.csv` | The output (generated by running `main.py`) |

## How to run

```bash
python main.py
```

This reads the two CSVs in the current directory and writes
`golden_customers.csv`.

To run the tests:

```bash
python -m pytest test.py -v
# or, without pytest installed:
python test.py
```

## Approach

The two sources have different columns, formats, and quality problems, so the
pipeline works in four stages.

### 1. Standardise each source

Both files are read into one common record shape. During loading, every field
is cleaned:

- **Emails** are lower-cased and trimmed, so `John.DOE@X.com` and
  `john.doe@x.com ` are treated as the same address.
- **Names** are trimmed and title-cased.
- **Phones** are reduced to digits only. The transaction file stores many
  numbers as raw digits while the CRM uses a `+` prefix; stripping non-digits
  lets the same number compare equal.
- **Dates** are standardised to ISO `YYYY-MM-DD`. Both sources mix ISO dates
  (`2024-01-06`) with a compact form (`20240106`); unparseable values become
  empty.
- Missing values everywhere become empty strings rather than `None`.

The CRM `customer_id` and transaction `transaction_id` are kept as
`source_id`, and each record is tagged with its `source` (`CRM` or `TXN`).

### 2. Match records to a single customer

Each record is assigned an identity key using the best identifier available,
in this order:

1. **email** — the most reliable identifier when present
2. **phone** — used when email is missing
3. **first + last name** — a last resort

Records sharing a key are treated as the same customer. Email is preferred
because it is the strongest unique signal; phone and name are fallbacks so
records with blank emails (present in both files) are not silently dropped.

### 3. Merge each group into one golden record

For every field, the value is chosen from the **most recent** contributing
record, using the record's event date (CRM registration date or transaction
purchase date). Newer data wins; empty values are skipped in favour of any
non-empty one. This keeps the golden record current without discarding older
records that fill gaps.

Each golden record also carries provenance:

- `sources` — which systems contributed (e.g. `CRM;TXN`)
- `source_ids` — the original IDs behind the record
- `record_count` — how many source rows were merged
- `last_event_date` — the most recent activity date across the group

### 4. Assign IDs and write output

Each golden record gets a stable `GOLDxxxxx` ID and is written to
`golden_customers.csv`.

## Output columns

| Column | Description |
|--------|-------------|
| `golden_id` | Unique golden record ID |
| `first_name`, `last_name` | Best (most recent) name |
| `email`, `phone` | Standardised contact details |
| `address`, `city`, `country` | Best (most recent) location |
| `last_event_date` | Most recent activity date across sources |
| `sources` | Contributing systems |
| `source_ids` | Original source record IDs |
| `record_count` | Number of source rows merged |

## Data quality issues handled

- Mixed date formats (ISO and compact 8-digit)
- Inconsistent phone formats (`+44...` vs raw digits)
- Blank emails in both sources (matched on phone/name instead)
- Whitespace and letter-case differences in emails and names
- Duplicate customers within the CRM file, and the same customer appearing in
  both sources

## Assumptions and possible extensions

- Matching is exact after cleaning. Typo-level fuzzy matching (e.g. similar but
  not identical names) is out of scope but would be the natural next step.
- "Most recent wins" is the merge rule; a source-priority rule (always trust
  CRM over transactions, say) could be swapped in inside `pick_best`.
- A single national phone format could be enforced if the country dialing code
  were known reliably.
